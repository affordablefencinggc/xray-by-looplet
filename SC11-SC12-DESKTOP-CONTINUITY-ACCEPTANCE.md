# SC-11 / SC-12 Desktop Continuity Acceptance

Status: planning only. Every `DC-*` row is pending. This document defines future acceptance; it does not claim that a build, sidecar, installer, archive, offline mode, or clean-machine run has passed.

## Purpose and authority

This plan decomposes the master-ledger SC-11 and SC-12 requirements into an ordered, machine-verifiable desktop and continuity programme. It is grounded in:

- `XRAY-MASTER-LEDGER.md` (SC-11, SC-12, feature inventory, and proof matrix);
- `XRAY-WORKBENCH-CONTRACT.md` (canonical state, ten-pane ownership, truthful capability boundaries, responsive proof scenarios);
- `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `src-tauri/src/lib.rs`, and `engine/host/src/lib.rs` (current desktop bridge and packaging surfaces);
- `scripts/build-sidecar.mjs`, `package.json`, `vite.config.ts`, and `vite.config.spa.ts` (current build paths);
- `src/studio/persistence.ts`, `documents.ts`, `documentContract.ts`, `evidence.ts`, `bomPersistence.ts`, `bomState.ts`, and their tests (current reload/integrity boundary);
- `screenshots/feature-audit.json` and the workbench audit scripts (current ten-pane browser inventory).

SC-08 owns the canonical proof-pack content contract. SC-12 must reuse that manifest and byte-selection contract rather than invent a competing archive. SC-11C must reuse the SC-07 typed transport rather than create another engine protocol.

## Current-state findings that must not be mistaken for acceptance

1. Tauri currently invokes `npx vite build --config vite.config.spa.ts` directly and consumes `../dist`; this bypasses the repository's app-environment wrapper and is not proof that the current supported app was packaged.
2. `tauri.conf.json` currently copies `engine/python` as a resource and has no required `externalBin`. `scripts/build-sidecar.mjs` searches PATH and a user-specific Python location, invokes an unpinned PyInstaller, may exit successfully with no artifact, and emits no checksum/provenance manifest.
3. The Rust host now fails closed unless `XRAY_ENGINE_PATH` names an executable; it deliberately has no source-tree, `engine/bin`, or PATH-Python runtime discovery. Packaging must bind the reviewed sidecar explicitly without restoring those fallbacks.
4. The native bridge already keeps import (`xray_import_plan`) separate from BOM status/run/cancel, validates source bytes, uses blocking workers for engine work, and cancels active work on close/exit. Unit proof is not packaged-process proof.
5. Job metadata uses `xray:fencing-job:v2` in `localStorage`; job-scoped BOM state uses `xray:bom-state:v1:*`; plan originals use IndexedDB `xray-plan-content-v1/documents`; photo originals use `xray-photo-content-v1/photo-content`. Retrieved originals are rehashed, but these stores are not one atomic, portable job archive.
6. Ordinary web reload is already evidenced. There is no complete archive, storage quota/eviction policy, service worker, CacheStorage policy, cold-offline proof, clean-machine installer proof, or no-network packaged proof.
7. The current Windows installer configuration is `currentUser` NSIS with `downloadBootstrapper` WebView2. Product name, identifier, version `0.1.0`, icons, package contents, upgrade identity, and uninstall residue still require explicit release evidence.
8. Existing `engine/bin/xray-engine.exe`, `src-tauri/bin/xray-engine-x86_64-pc-windows-msvc.exe`, `src-tauri/target/**`, and generated installers are untrusted inputs until a reviewed build establishes their provenance. Their presence proves nothing.

## Proof vocabulary and safety gates

The commands below are acceptance command contracts to be implemented in the named slice. A row passes only when the command exists, exits zero, writes the named JSON/JUnit evidence, and the evidence is attached to the exact source commit and artifact SHA-256. “Native” means a real Tauri window and reviewed packaged sidecar. “Clean machine” means a reset Windows VM with no Python installation and no repository checkout. Browser proof is allowed only where explicitly stated and never substitutes for a native row.

- `FB`: `node scripts/verify-tauri-current-build.mjs --json proof/SC-11/frontend-build.json`
- `SB`: `node scripts/verify-sidecar-package.mjs --json proof/SC-11/sidecar-package.json`
- `PT`: `cargo test --offline --manifest-path engine/host/Cargo.toml` plus `cargo test --offline --manifest-path src-tauri/Cargo.toml`
- `PN`: `node scripts/audit-packaged-workbench.mjs --evidence proof/SC-11/packaged-workbench.json`
- `CI`: `powershell -NoProfile -File scripts/windows-clean-install-audit.ps1 -Evidence proof/SC-11/clean-install.json -VmSnapshot clean-no-python`
- `AR`: `node --experimental-strip-types --test src/studio/archive*.test.ts` plus `node scripts/verify-job-archive.mjs --json proof/SC-12/archive.json`
- `OF`: `node scripts/offline-continuity-audit.mjs --json proof/SC-12/offline-continuity.json`

These harnesses must accept only artifacts produced in the same reviewed pipeline and named in an immutable build manifest. They must refuse absent/mismatched hashes. No acceptance step may execute repository-found or downloaded `.exe`, `.msi`, sidecar, installer, shell script, or arbitrary fixture merely because it exists. No network is permitted during sidecar execution or packaged no-network proof. Installer/network tests, when approved, use only the exact signed candidate in an isolated disposable VM. Tests create harmless temporary fixtures and remove them after evidence capture.

## Required proof records

Every generated JSON record must include `schema`, `caseId`, `status`, UTC start/end, source commit, dirty-tree disclosure, command argv, platform/OS build, architecture/target triple, build ID, artifact path relative to the evidence root, artifact SHA-256, sidecar provenance-manifest SHA-256 where relevant, fixture IDs/hashes, exit code, assertion list, capture paths/hashes, and `proofSurface` (`static`, `unit`, `browser-dev`, `browser-built`, `native-debug`, `native-release`, or `clean-machine`). Native records must include app executable and child sidecar image identity. Clean-machine records must include VM image/snapshot ID and preflight inventory proving no Python/repository toolchain.

A passing aggregate with a missing row, a skipped required test, an ignored fixture, an unexpected network request, an unreviewed artifact hash, a dirty-tree ambiguity, or a browser/native provenance mismatch is a failure. Conditional web-offline rows must record the ADR branch; they are not silently skipped.
