### SC-07's proof was racing React (2026-09-19)

Re-running `qa-sc07-final` against the committed tree passes — four times over (`24.2 s`, then three consecutive runs). The two earlier `exit=1` runs in `proof/growth/runner/` were not flakiness and not a product defect. They were the proof asserting too early.

The old scenario combined the restore click and its assertion in a single `eval`:

```js
document.querySelector('[data-testid="tamper-simulate"]').click();

if (card.getAttribute('data-seal-status') !== 'verified') throw Error('Seal did not restore');
```

`setTampered` is a React state update. The click schedules it; it does not apply it. Confirmed by op alignment — the 41-op scenario is the 39/40-op sequence with exactly that one op split, and nothing else differs. Run `2026-09-19T04-32-36-149Z-qa-sc07-final` (exit 0) is the first run of the corrected scenario, three seconds after the last failure.

## SC-09 — QS item-level evidence binding (QS-03) (2026-09-19)

Every cost-plan row can now be bound to the measured entity its quantity came from, and the binding carries the entity's SHA-256 geometry hash and the calibration it was measured under. Whether a binding still holds is **derived on every render** from the live entity, never stored — `evaluateItemBinding(binding, entity)` is a pure function, for the same reason `frozenDeliveryState` is. A stored verdict would be a second source of truth, and the copy is the one that goes stale.

**The slice's first real finding was that the ledger could not fail.** The panel originally re-derived the binding and the entity from the same current row values, so `evaluateItemBinding` was comparing a hash against itself. Typing `99` into a row that was measured at `45.5` left it reading `verified` — a ledger that reports a clean verification no matter what the user enters proves nothing, which is the exact failure mode this slice exists to prevent. The fix separates the two halves: bindings are **pinned** when the draft is calculated (the numbers the user confirmed), while entities are re-derived from the **live** rows on every change. An edit moves the entity out from under the pin and the row goes stale. The rule lives in `shouldRepin()` in [qsItemBinding.ts](src/studio/industries/quantity-surveying/qsItemBinding.ts) as a pure function, because it cannot be reached through a render: the panel emits the same markup whether or not it re-pinned on the way there.

Two further defects were found and fixed on the way. Editing a quantity withholds the report (`calculated: false`), and the ledger sat inside `{report && …}` — so the evidence table unmounted on the user's first keystroke, exactly when they needed it. It is now rendered from the draft's own rows and hoisted outside the gate. And `unverifiedCount` excluded unbound items, so a draft with nothing bound withheld pricing silently; it is now `withheldCount` and counts an unbound row as the weakest state of all.

Executed: `node scripts/fast-cdp-test.mjs qa-sc09-final` — 28 opcodes, exit 0, zero console errors. The scenario asserts in **both** directions: a freshly calculated draft shows 3 rows `verified`, no withheld notice and `Permitted` pricing; typing `99` into row 1 turns **only** that row to `stale-measurement` with pricing withheld while the other two stay verified, and the notice names `1 stale-measurement`; restoring `45.5` returns every row to verified with the notice gone. An earlier run that asserted only the withholding is retained in the runner logs — a guard that only ever withholds is indistinguishable from one that withholds unconditionally.

Captures inspected at desktop 1600×1000 and tablet 1024×768: three verified rows with real digests (`8792380e980a…`, `112e206cb839…`, `3b3fe9931bf8…`), the stale state showing `99 m3` against a bound entity of `45.5 m3` with the reason *"Entity measured:Bulk Trench Excavation geometry changed since the item was measured."*, and the recovered state.
