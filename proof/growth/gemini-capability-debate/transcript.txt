🏛️ Engineering Diagnosis: Parametric BIM vs Generative 3D

When Gemini chat produces an impressive 3D scene, it typically writes arbitrary Three.js scripts, loads unconstrained polygonal meshes (GLTF/OBJ), or applies custom GLSL shaders and studio lighting.

X-Ray operates under an entirely different paradigm: it is an authoritative, multi-layer parametric BIM kernel (xray.architect/v1). Every element must maintain strict topological relationships, layer assemblies, level datums, opening host constraints, and DXF/IFC export integrity.

1. Hard Schema and Engine Limitations

These are mechanical boundaries enforced by the workbench schema and tool APIs (read_workbench_structure, draw_architect_elements):

Limited Authored Primitives: draw_architect_elements only accepts level, wall, door, window, slab, roof, line, room, footprint, and extrude. It cannot author columns, stairs, railings, curtain walls, solar panels, or site terrain—even though some of these exist as read-only categories in cataloged source reconstructions.
Strict Planar and Host Constraints:
Walls are strictly vertical linear segments (A \to B) between level boundaries. Slanted walls, battered walls, or spline surfaces cannot be expressed.
Openings (door, window) can only exist if hosted inside a wall segment with a linear offset, width, height, and sill. Free-standing glass facades, glazed roofs, or ribbon glazing spanning multiple walls without solid hosts are rejected by schema validation.
Roofs must be closed convex polygons with edge-based pitch/gable definitions. Concave profiles, domes, barrel vaults, and hyperbolic paraboloids cannot be represented as a single entity.
Append-Only Batches: Geometric authoring is capped at 25 operations per batch call (≤25 operations per batch, with caps of ≤100 levels and ≤3000 walls). Complex assemblies must be partitioned across serial turns with revision synchronization.
No Direct Viewport Injection: Geometry cannot be injected straight into the 3D Model viewer (notAvailableThroughTools). Geometry must be authored in Sketch through draw_architect_elements and projected into Model mode via show_design_in_model.
2. Things Possible Now but Extremely Laborious

The system is capable of far more complexity than a simple rectangular building, but achieving high architectural fidelity requires intensive manual mathematical calculation:

Faceted Curvature: While curved walls do not exist as primitives, true curved forms (cylinders, rotundas, serpentine walls) can be constructed by discretizing curves into 24–48 linear wall segments across synchronized levels.
Stepped Massing, Cantilevers, and Lightwells: Slabs accept arbitrary polygons with 3 to 200 vertices, custom thickness, and vertical offset. By combining custom slab boundaries with staggered wall offsets across multiple levels, you can generate deep cantilevers, stepped sky gardens, and multi-storey interior atria.
Dense, Articulated Facades: Instead of generic flat walls, you can model rich architectural relief by breaking facades into alternating pilaster wall runs, recessed glazing bays, and dozens of rhythmically distributed hosted windows with varying sill heights.
Multi-Zone Complex Roofscapes: Non-convex roof plans (L-shaped, U-shaped, courtyard enclosures) can be built by geometrically decomposing the roof into adjacent convex zones with calibrated pitches, eaves, gutters, and fascia offsets.
3. Workflow, Prompting, and Visual-Quality Shortcomings
Interactive CAD Shading vs Photographic Synthesis: The live 3D canvas is an interactive CAD viewport designed for spatial clarity, dimensioning, and drafting playback (control_draftsman), not photorealistic path tracing or cinematic depth-of-field. While generate_render_visualisation provides AI conceptual rendering on the web canvas, the interactive viewport itself prioritizes dimensional clarity over visual drama.
Default Prompt Conservatism: Language models routinely under-specify geometry when asked for a building, defaulting to a single-storey box or a uniform 4-wall extrude operation. Producing high-architecture forms requires prompting specifically for articulated massing, stepped terracing, and fenestration rhythm.
4. Claims That Cannot Be Verified
Client GPU / Frame Telemetry: The assistant cannot inspect real-time frame rates, draw calls, or WebGL shader bottlenecks on the user's specific client hardware.
Subjective Visual "Impressiveness": The visual quality of Gemini's arbitrary Three.js code cannot be evaluated objectively against X-Ray's structural output. Gemini's 3D scenes are decorative meshes that cannot produce IFC building data, multi-layer wall assemblies, or takeoff schedules.

Rank 1: Lack of a Transform / Array Tool

Extrusion operates vertically across levels, but horizontal repetition (structural column grids, facade mullions, rhythmic window bands, brise-soleil louvers) requires manually calculating coordinates for dozens of individual elements. The primary friction is not geometric representation, but the burden of generating verbose coordinate lists within token and round budgets.

Rank 2: Rigidity of the 2.5D Primitives

The geometry is planar and axis-constrained:

Walls are strictly vertical extrusions between level datums; canted, battered, or curved walls do not exist.
Roofs must be strictly convex polygons; an L-shaped or courtyard roof cannot be defined as a single entity and must be mathematically decomposed into multiple adjacent convex hulls.
Openings can only be hosted in walls; opening penetrations through slabs (stairwells, light shafts) or roofs (skylights) cannot be cut directly using opening tools, requiring slabs to be manually tiled around voids.
Rank 3: Spatial Planning Without Mid-Batch Geometry Feedback

The assistant authors blind coordinate sets. While show_design_in_model and capture_workspace_image provide visual confirmation after committing changes, there is no spatial query tool (e.g., raycasting, clearance checks, or bounding-box collision detection) to verify complex multi-tier clearances before issuing an edit batch.

Rank 4: Missing Specialized Primitives (Columns, Stairs)

As noted, a rectangular column is geometrically equivalent to a 4-vertex polygonal slab with a defined thickness and vertical offset, or a set of small wall segments. Missing dedicated primitives creates classification and convenience gaps, but does not prevent geometry creation.

🚫 What Cannot Be Adequately Approximated Today

While rectangular columns, stepped terraces, and faceted facades can be built using current tools, the following geometries cannot be modeled:

Non-Vertical Surfaces: Sloped curtain walls, battered stone plinths, ramps, battered retaining walls, or raked auditorium floors.
Compound / Curved Roof Forms: Barrel vaults, domes, saddle roofs, hyperbolic paraboloids, or continuous non-convex roof profiles.
Slab and Roof Voids: True negative volumes (punched openings for lightwells or skylights in a continuous slab) cannot be cut; the enclosing element must be segmented into multiple abutting polygons.
Non-Planar Wall Trajectories: True splines or Bézier curves (faceted approximations create high entity counts and imperfect corner joins).

⚖️ First Extension Choice: Array Tool vs Column vs Procedural Geometry

Selection: Transform / Array Tool

Why not Native Column? A column is syntactic convenience. A column can be placed today by drawing a 400 \times 400\,mm slab with a 3{,}000\,mm thickness and vertical offset. Adding column saves a few coordinates per instance, but adds zero new geometric typologies.
Why not Bounded Procedural Geometry first? Procedural geometry (e.g., generating parametric stair towers or truss webs) adds heavy engine complexity and schema burden before addressing the authoring bottleneck.
Why the Transform / Array Tool is superior:
An array operation (linear and grid with counts, spacing vectors, and target IDs or template payloads) solves the fundamental LLM limitation: token budget exhaustion and arithmetic drift when generating structural grids, balustrades, repetitive fenestration, or colonnades.
It turns a 50-operation fenestration batch into a single structured directive, unlocking dense, highly articulated facades.

🏛️ Smooth, Curved, and Twisted Structures

A procedural tool generating current primitives can only approximate curvature via segmented, faceted chords and tiered polygonal slabs. True curved and twisted topology requires new native primitives:

Non-planar / Ruled surfaces: Hyperbolic paraboloids, lofted skins between differing floor profiles, and twisted facades require native b-spline, NURBS, or quad/triangle mesh surfaces.
Curved linear elements: Arc- and spline-based wall baselines with analytical radial offsets.
Freeform openings & penetrations: Openings not rigidly bound to vertical linear wall hosts (e.g., diagrid fenestration, 3D surface perforations).
