How to read this page

Two instruments produced it, and they are not equally strong.

  • live Executed. A real provider turn ran through the shipped UI and the result was read from the app's own archive, the DOM, or both. Runner ids and screenshot paths are given so any run can be re-read.
  • source / verified I read the code. The claim is grounded in a cited file:line that I opened myself this session.
  • mapped Reported by the map workflow. Nine cluster agents built a map of the assistant surface and a tenth critiqued it; a verifier overturned claims lacking source. I did not independently re-verify every row flagged this way. This is the weakest tier and is marked wherever it appears.
  • not tested Open. Named in §4 so the gap is visible rather than implied by silence.

The map is reproduced in full in §3, converted from assistant-map.md in this directory at build time rather than retyped, so the text is the map's own words rather than my transcription of them. That removes transcription drift, not every form of drift — the conversion is a small hand-written markdown reader rather than a markdown implementation, and a review of this page caught it silently eating the glob asterisks in the map's own code spans (import_*, quote_*). That is fixed. Where the map and I disagree, or where the map is wrong on its own terms, the disagreement is stated in §3 before the map begins rather than reconciled silently: a map quietly corrected while being reproduced is a map you cannot trust either way.

How much of this register survived an attempt to falsify it

Nothing on this page is here because it was written confidently. Every factual claim was handed to four independent passes whose instruction was to destroy it — find the citation that does not say what the page says it says, the run that does not show what the page says it shows, the mechanism that cannot work — and to default to refuted when uncertain.

Pass one audited 55 claims across six areas against their cited sources. Forty-three survived intact, eleven were refuted or narrowed, and one could not be settled either way. Pass two took the page as a whole and attacked the load-bearing claims again from the source, which is where the corrections below come from. Pass three attacked the corrected page itself, and found two of the worst items in this list: a correction §1’s own list certified as applied while §2 still carried the uncorrected sentence, and a defect row whose arithmetic disagreed with the map row three rows below it — the same failure, on the same six branches, that the row was written to correct. Pass four attacked the corrected page again through four lenses at once — the restart bullets and every count in them, the defect register’s arithmetic, the process record, and this page’s internal consistency — and found that the second of those fixes had reached only half of its row: D4’s arithmetic was corrected in the evidence cell while the defect sentence above it kept the old wording, under a §1 bullet that had already certified the whole row as reading “3 + 1 + 2”. That lens and the three beside it produced fifteen items between them; the fourteen that are not the D4 cell are named in the record’s corrections table, and five of them are on this page. Every one is fixed in place rather than in an appendix. Eleven cut against this page’s own interest, which is the point of recording them:

  • D8’s live tier is withdrawn. The run cited for it never called an edit tool, so editToolsSucceeded: 0 counted zero successes out of zero attempts. D8 is now live for the admit half only.
  • D1’s mechanism was eliminated, not just doubted. The page had proposed that the leaking turn began with a work packet carrying lastFailure. Work packets have no such field; it belongs to routing state, which starts empty for a new chat. The proposed cause cannot happen, and the section above says so.
  • D1’s rate was overstated in an earlier draft as “one in three with an identified trigger”. Two runs made to test the trigger did not reproduce the leak, so it is one in five with no known trigger.
  • D1’s character count was one high. 159 is the stored entry including its trailing newline; the reasoning sentence is 158.
  • D6 named the wrong mode. The page described readonly behaviour and cited a mechanism that readonly never reaches. It is an ask-mode defect, and the fix the page proposed would not have changed readonly at all.
  • The rightcontext attribution was asserted, not shown. No raw provider output is archived for that turn, so the page now presents stripReasoning as a confirmed way this weld happens rather than as what happened here.
  • This page’s own reading of the map row it calls M5 was wrong in both directions. It counted four dead branches in describeToolIntent by mixing two rules, and said the map’s “six” could not be reconstructed. Counted by one rule there are three, by the other six, and the map’s “six” is the second of those. The map’s sentence is still incoherent — it glues the two counts together — but this page had no business calling one of its numbers unreconstructable, and §3’s M5 row now says so.
  • Three statements in the restart bullets were stronger than their record. The close/relaunch experiment was described as repeated “under a second name” when both pairs ran under qa-live-10-ask-mode-deny; the relaunch’s new daemon and browser were given as fact from a process table no log holds, when the run’s own log carries no launched browser line at all — the builder that made the run requires one, which is how the discrepancy surfaced; and the sentence that a reused session name carries state only while its browser is still running is true of the default profile only, which the persistent-profile experiment in §2 is the counterexample to. Scenario 09: what read-only mode actually did

This is the second place an earlier draft of this page claimed more than its evidence, and the correction is worth reading in full because the mistake is an easy one.

Two things follow. First, the provider does not stream — MiniMax returns one complete message per round — so every provider round becomes a separate user-visible bubble. A five-round turn is five bubbles interleaved with tool cards, not one answer that grows. That is a presentational fact worth deciding on deliberately.

Second, stripReasoning (src/lib/minimaxAi.server.ts:122-131) is a confirmed way for words to end up welded: it deletes a closed <think>…</think> block by replacing it with the empty string — no separator, no space — so the text either side is joined, exactly the shape rightcontext has. Whether that is what produced this instance is not established. No raw provider output is archived for the turn, so nothing distinguishes “a reasoning block was deleted here” from “the model wrote rightcontext as one word”. The defect is real either way; the attribution is a source-grounded explanation that the evidence cannot close, and it is recorded as such rather than asserted.

The gate itself held: denialReachedModel: true, saveToolsSucceeded: 0, the archive revision unchanged after the denial, and the reply withdraws the action rather than claiming it. That is the behaviour the source says should happen, observed under a model that was actively trying to save.

What the harness turned out to be

Five facts about the rig were established by direct experiment this session, and each one changes how a result must be read.

  • The browser profile is keyed by session name. Scenario 19 writes a sentinel only if none is present. First run of a new session name: “fresh profile — nothing was here”. Second run, same name, six and a third seconds after the first (00-24-35-797Z then 00-24-42-130Z): “state survived a previous run” — the sentinel present in both localStorage and IndexedDB, alongside a real project id. This reconciles two facts that looked contradictory: the first sweep's re-run returned the previous run's identical answer (it reused the name qa-live-03), while scenarios 18a and 18b shared nothing (different names). A reused session name carries state; a new one starts clean. The restart experiment below sharpens that: under the harness’s default profile a reused name carries state only while its browser is still running, because there the name is a key to a live browser rather than to a directory that outlives it — and the persistent---profile experiment three bullets later is the exception that proves the qualifier: with a profile directory the harness is told to keep, the state does outlive the browser. Any scenario that must start empty has to assert emptiness itself, exactly as the corrected harness does — a fresh-looking run is not evidence of a fresh profile.
  • An earlier draft of this bullet claimed the chat archive survives a full browser restart. That claim was wrong, and the way it was caught is worth keeping. Scenario 17 enumerates the chat-history database and originally failed with “No archived projects at all” — because it ran under a brand-new session name. The re-run cited for the claim, under qa-live-10-ask-mode-deny, found the archive intact: project job-b9ac9b63…, revision 115, 6 threads, 11 assistant entries, 3 user entries, 12 tool entries, last user message preserved verbatim. But that run attached to the browser the earlier run had left running. Sixteen runs now exist under that session name. Three logs in them print launched browser: the very first run of the name (00-06-09-162Z) and the two relaunches made for the experiment below. The thirteen in between — the cited 00-24-53-030Z among them — print none, because each one attached to the browser the first had started. Nothing had been restarted, so nothing about a restart had been tested. (The count moved from fifteen to sixteen after this page was first built, and this campaign moved it: closing that browser at the end of the sweep is itself a run under the same session name, 01-11-40-522Z, and it is one of the thirteen that print no launch line. Three still launch, thirteen still do not, and the ratio is a property of the session name rather than of the scenario file.)
  • A restart does end the state: the harness's default profile does not survive it. Closing that browser (run 00-49-12-852Z, whose log is 19 bytes and reads ✓ Browser closed — that line is the file) and re-running the identical scenario file — same sha256 5c5432fe… as the pre-close run — produced launched browser and then “No archived projects at all”, where the pre-close run had read 8 threads out of that same database seconds earlier. Repeated a second time under the same session name, same result (close 00-51-16-968Z, relaunch 00-51-19-369Z, empty archive). The cause is on disk: the default profile is a per-launch temporary directory, %LOCALAPPDATA%\Temp\agent-browser-chrome-<guid>, one per browser. The GUID seen in use before that close (8f23daef-cf67-4a2a-8d40-9043c348…) was gone afterwards and the relaunch came up under a different one (a308e756-6d20-4cc3-8b9a-85f98a45…) — those two were read off the screen, and the second is now archived: the process table kept with this review (process-table.json) records, for each session this campaign ran, its daemon PID, creation time, executable and the profile directory the browser was launched against, and re-checks whether that directory still exists once the browser is closed. The campaign could not have shown restart persistence this way, and the open gap it claimed to close was still open.
  • Asked properly, the answer is yes. The CLI accepts --profile <dir> for a profile that is allowed to persist, so the same experiment was run against one. Run 00-50-26-966Z seeded a project into a persistent profile, sent one live turn carrying the sentinel reference RSTRT-21-A7, and ended with ✓ Browser closed. Run 00-50-49-888Z then re-ran the read against that session name and that profile directory — the two commands differ only in which scenario file they pass, and both carry --profile .temp/live-rig/chrome-profile-restart (the commands are written out in the reproduce block below; the runner’s report holds no profile field, and the process table records the directory that argument produced rather than the argument itself — the userDataDir it carries for that browser is .temp/live-rig/chrome-profile-restart, the one entry in the whole record that is not under %LOCALAPPDATA%\Temp) — and found the sentinel in the archive, thread a73eca33…, with the app's own conversation view rendering the turn and its tool rows. Two things about that run are worth stating plainly. Its log carries no launched browser line, although the builder that made it requires one, so the browser start rests on the process table instead: process-table.json records daemon 32024 alive since 10:50:49 with browser 84336 created at 10:50:50 under that profile directory — the relaunch second, and the only session here whose browser is not using a temporary profile. And the two screenshots filed for this experiment, 21-restart-after-read.png and 21-restart-after-ui.png, are byte-identical (sha256 1b012ff9…, 145 572 bytes each, both written at 00:51:49 — that is, by the corrected 21b UI run 00-51-48-501Z, which runs the same 12-opcode scenario and overwrote the frames the read run above had written a minute earlier, so the pair on disk proves the frame, not that run’s frame), which is what a persistent profile restoring the panel already open would produce: the capture taken after the panel is opened is the same frame as the one before it. So persistence across a browser process ending is real for the app's IndexedDB archive; what failed was the harness's default profile, not the app. This closes the gap the bullet above only appeared to close.

The thread the instrumented scenario-10 run (00-20-23-609Z, the one whose captured rows match its archive thread) wrote holds 1 user + 5 assistant + 4 tool entries — the same ten rows the DOM capture counted, by a different instrument.
