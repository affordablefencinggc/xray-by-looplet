# QS-01-SC-01 — Ground the CSV/hierarchy explanation in tool output

Status: implemented and verified against actual exported bytes, a current tool receipt and a reloaded browser session. Live provider/Developer answer quality remains OPEN (no model call was made in this batch).

## Requirement

From [the plan](../../../../INDUSTRY-REMAINING-WORK-PLAN.md) QS-01 and [the QS report](../../../../planning/industry-work/quantity-surveying-report.md): the assistant answer and Developer review "remain inaccurate about CSV hierarchy fields and why inclusive totals are safe." The explanation must convey that the CSV holds one row per actual item including parent-direct assignments with no rollup records, that hierarchy fields are retained, and that inclusive parent/child totals overlap and must never be added — the report total is safe because each actual item is counted exactly once.

## Root cause

Both recorded failures in [the prior live review](../../2026-09-13-industry-agents/quantity-surveying/report-upgrade/live/REVIEW.md) were inferences the tool payload never supplied:

1. "Claimed no parent labels in CSV despite classification-path fields." `quantityReportCsv` lives in `report.ts` and is called only by `QuantityReportView.tsx`. The assistant tool returned **nothing about the CSV at all** — not the columns, not the row rule. The model described an export it had never been shown.
2. "Attributed safe rollups to evidence classes being disjoint across parents." The payload returns `nodes[].direct` and `nodes[].rollup` as bare arrays with no statement that `rollup` re-counts descendants. For the fixture below the model sees `Building` carrying 0.3 m2 and `Walls` carrying 0.3 m2 and must invent a reason why adding them is wrong.

The pre-existing description line "use report totals for reconciliation rather than summing ancestor rows" states the conclusion but supplies neither the CSV facts nor the overlap mechanism, so it did not prevent either error. `appTools.ts` passes `...result` through verbatim as JSON text, so anything added to the returned object reaches the model with no root integration.

## Exact diff

[Source diff](../source.diff) — `report.ts`, `assistantTool.ts`, `assistantTool.test.ts` only. No forbidden file touched.

- `report.ts`: extracted the export header into an exported `CSV_COLUMNS` constant and built `quantityReportCsv`'s header from it, so one definition serves both the export and the assistant boundary.
- `assistantTool.ts`: added a `reportContract` object (csvColumns, csvRowRule, csvHierarchyRule, totalsRule, rollupOverlapRule, reconciliation) returned on every `execute` result, and corrected the tool description to explain the mechanism instead of only asserting the conclusion.

New tests bind the explanation to the real export rather than to prose:

- `result carries the real CSV columns so an explanation never has to infer them` — asserts `reportContract.csvColumns` deep-equals the header parsed out of the bytes `quantityReportCsv` actually writes. If a column is added and the contract is not updated, this fails instead of the assistant silently resuming a false description.
- `result states item-once aggregation, not disjoint evidence, as why inclusive totals are safe`.
- `inclusive rollup demonstrably re-counts descendant items rather than adding new ones` — `Building` holds no direct m2 item, so its 0.3 m2 is entirely `Walls`'s items re-counted; summing 0.3 + 0.3 would double-count while the item-once total stays 0.3.
- `tool description explains the CSV and overlap mechanism it previously only asserted`.
