# Recoverable backup → editing-workspace apply

Read-only design audit, 2026-09-07. This is an implementation plan, not a completed feature. Scope: apply the verified main-workspace package already supported by `projectBackup.ts`; preserve existing originals, recover the previous workspace after a failed or interrupted apply, and prevent another X-Ray window from writing across the restore. No source was changed during this audit.

## What the current implementation already provides

- `src/studio/projectBackup.ts:102` validates job schema, each saved module, exact original identities, decoded bytes, SHA-256, MIME and page counts. `backupPhotos` at line49 includes inactive document-workspace photos. Reuse this validator before planning any mutation.
- `src/studio/projectBackupStorage.ts:104` reads a stored package and verifies the catalogue's byte length and SHA before parsing it. A library selection must use `readProjectBackup`, not trust the UI's cached preview.
- `src/studio/projectBackupStorage.ts:27` is the current explicit record capture allowlist. Extend this mapping into a restore plan rather than enumerating arbitrary localStorage keys.
- `src/studio/projectBackupStorage.ts:90` stores an immutable package and summary in one IndexedDB transaction. Reuse `storeProjectBackup` to make a visible “Before restore” recovery backup of the current committed workspace.
- `src/studio/ProjectBackups.tsx:51` already refuses backup capture until hydration is ready and persistence errors are resolved. Applying is explicitly unavailable in its scope copy. Add an apply preview here only after the transaction coordinator exists.

All `records.* === null` values in a v2 package mean an absent saved record for that mapped scope. Restore them as absence, using recorded before-images; do not merge old target-project data into the snapshot. For old v1 packages, sheetMetadata/priceBooks were not captured at all. Preview must disclose those unsupported fields; either keep them explicitly or require a supported v2 package for a complete replacement. Do not pretend absence in v1 proves the older snapshot intended to erase them.

## Concrete hazards to resolve first

1. `store.ts:2396` autosaves every hydrated job object change immediately; `2403` saves BOM and `2412` saves inventory. Setting a new job with hydration still enabled can write partial state. `store.ts:2389` also reconciles BOM as soon as job changes, independent of hydration. A simple `setState({job: backup.job})` is unsafe.
2. `hydratePersistence` at `store.ts:2187` returns early once hydrated. Calling it after overwriting storage does not reload the existing editor. Its body clears object URLs, rebuilds markups/calibration, resets selections and trace history, checks original bytes, reconciles BOM and may mark an interrupted BOM build failed. Reuse this boot path through a controlled full reload after committed apply, not a second ad hoc hydration implementation.
3. `Studio.tsx:86` begins hydration on mount. Startup replay must finish before this call and before any module can save. Current hydration can finish with `hydrationStatus: "ready"` even if a source is missing/corrupt, so apply must additionally inspect runtime asset readiness and module errors before declaring success.
4. Architecture keeps session and undo/redo in `architect/ArchitectWorkspace.tsx:143`; it reloads on job ID change, not same-job revision change. Its storage event listener at151 does not receive same-window writes. A complete root remount/reload is required for same-ID restore. Other module panels have the same issue: `ProjectMaterialsPanel.tsx:74`, `SourceTakeoffPanel.tsx:24`, `ConnectionTrialPanel.tsx:34`, `pricing/PriceBookPanel.tsx:26`.
5. `store.ts:1309` source import awaits original storage, then uses `documentSelectionVersion`; photo import at2015 writes before applying the job; BOM requests can remain in flight. A frozen button alone does not stop late promises from writing. Central write permission must be checked at persistence boundaries as well as UI entry points. Drain existing writes and invalidate outstanding operation epochs before exclusive restore.
6. Material scans have an AbortController (`ProjectMaterialsPanel.tsx:61`) and unmount abort; `architect/SyncDesignMaterials.tsx:46` guards job ID/design revision but can still be saving. Price book imports guard generation at `PriceBookPanel.tsx:25`. Restore must cancel/drain these; source/job equality alone is insufficient when restoring an older revision with the same job ID.
7. There is no browser transaction spanning localStorage and the three original/material IndexedDB databases. Best-effort sequential writes without a durable journal cannot satisfy crash recovery.

## Minimal new coordinator and window guard

Add `workspaceRestore.ts` (pure plan/phase logic), `workspaceRestoreStorage.ts` (journal and allowlisted adapters), and one shared `workspaceWriteGate.ts`. Preserve existing domain schemas, storage keys and original IDs.

Use one origin-wide Web Lock, `xray:editing-workspace`, with shared leases for normal editing windows and an exclusive lease for restore/startup replay. A normal window may write only while its shared lease is live. It must hold that lease through completion of any in-flight persistence transaction. This allows normal multiple windows without changing all synchronous persistence APIs into queues.

On restore request, broadcast `prepare-restore` with an operation ID. Each updated window freezes editing, aborts cancellable work, waits for registered writes to finish, invalidates async operation epochs, and releases its shared lease. The initiating window does the same. Acquire the exclusive lock with a bounded timeout; refusal leaves the existing project intact. Broadcast acknowledgements are for UI status; only the lock proves the exclusion. If Web Locks are unavailable, keep apply unavailable rather than claiming cross-window safety.

Every covered writer must consult the shared gate synchronously before starting a write. Guard the top-level job/BOM/inventory subscribers and the adapter entry points in the table, plus source/photo writes and material sync. Async writers register an in-flight promise; they may not acknowledge quiescence until it settles. After the exclusive lease, acquire sheet/price per-key locks in sorted-key order. All code must acquire workspace lease before any per-key lock, avoiding reversed-order deadlocks.

Older app windows that predate this gate cannot cooperate. Detect participating build/protocol through a heartbeat registry for updated windows, warn that older versions cannot share the profile, and retain before-value verification; do not claim those checks alone make an uncooperative old binary safe. Native launch/update policy must prevent mixed-version writable profile sessions or apply must refuse that scenario. An advisory localStorage flag is not a substitute for the Web Lock.

## Apply sequence

1. **Preview only:** read and revalidate selected backup, build the full explicit storage plan, show incoming/current project names and revisions, originals/modules affected and exclusions. Capture an expected current workspace fingerprint including raw job, per-module raw strings and material raw value. Cancel changes nothing.
2. **Quiesce:** enter the window guard and acquire exclusive workspace lease. If current fingerprint differs from preview, refuse and rebuild preview. Require current source/evidence and saved modules to be readable; otherwise do not overwrite them through ordinary restore. A separate recovery mode would need its own raw-export proof.
3. **Preserve current project:** capture/validate/store a “Before restore” backup with current committed work. This backup remains visible even if apply succeeds. Capture additional raw before-images for every destination key, including another project's already-saved modules when restoring a different job ID; current-project backup alone does not preserve those target collisions.
4. **Prepare durable journal:** new IndexedDB database `xray-workspace-restore-v1`, stores `operations` and `payloads`; write one operation with unique ID, protocol version, incoming/recovery package IDs and digests, exact raw before/after map, asset plan and `phase: prepared`. Persist actual incoming package bytes or an immutable verified library reference before any active-key write. A localStorage startup marker is optional acceleration, never the sole recovery evidence. Failed journal creation means no apply.
5. **Preserve originals:** for every source/photo ID, transactionally reuse only byte-identical existing data; insert absent originals. Refuse same-ID/different-byte or conflicting metadata rather than overwriting or inventing ID remaps. Retain newly inserted originals on rollback as journalled unreferenced assets; do not delete them during the restore transaction. This avoids deleting files another surviving reference might use and preserves all original bytes.
6. **Write planned modules:** commit journal phase `writing`; for each mutation require the actual raw value to equal its expected before-image or already equal its after-image (idempotent replay). Replace/remove allowlisted per-project records and material raw values; read back exact bytes after every write. Update journal progress only after actual store commit. Progress flags are hints: replay must compare data because crash may occur between target commit and progress update.
7. **Switch active job last:** verify all originals and module after-images, then write the validated active job slot. Read back and parse. Keep gate closed. Write journal phase `committed` only after this whole persisted target state is verified. Any failure before committed triggers rollback below.
8. **Boot from committed storage:** use a controlled reload to clear all editor histories, module sessions, object URLs and stale closures. Boot gate acquires exclusive lease, sees committed operation and verifies target hashes/identities before hydration. After hydration confirms required plan/photo readiness and readable module state, record `verified`. Only then resume shared editing leases. Imported pending BOM work must become an explicit interrupted/recompute state through existing hydration, not a phantom completed quote.

The transition is a project replacement, not an undoable drawing edit. Existing drawing undo/redo cannot cross it. The prior project remains in the recovery library.

## Startup replay and rollback

- Run journal recovery before `hydratePersistence`, even if the small startup marker is absent. An unreadable journal/database keeps editing blocked and offers recovery download; never silently start default-project autosave over uncertain data.
- `prepared` with no active mutations: verify no unexpected target changes, abandon safely and retain recovery artifacts.
- `writing` without verified commit: roll back deterministically to raw before-images. Restore per-module raw values and material value, then original active job key. Originally absent values must become absent again; preserve legacy key as captured. Retain inserted original blobs and all backups.
- Before rollback of each key, accept only exact planned after-image or exact before-image. A third value means an external/uncooperative writer intervened: stop recovery and preserve journal, both packages and current bytes. Do not overwrite the third value as “rollback”.
- `committed`: complete verification and boot into target; do not roll back merely because acknowledgement was interrupted. Missing/corrupt after-images block editing and offer explicit recovery to the verified before-package. Keep journal until persisted state plus runtime verification pass.
- If rollback storage writes fail, retain `recovery-required`, keep editing disabled across reloads, and expose the already-persisted recovery backup. Do not clear journal because a cleanup step failed.
- Journal phase writes use one IndexedDB transaction per phase and readback. Never put plan/photo binary payloads in localStorage or rely on a `beforeunload` callback.

## Required refusal and recovery assertions

Implement failure-injection tests at every boundary, plus real browser proof before checking this item:

1. Cancel preview → all raw target keys and source/photo bytes unchanged.
2. Changed job, module, material or price/sheet value after preview → refuses before mutation; current state retained.
3. Missing/corrupt backup asset, invalid module JSON, different source SHA/page count, same original ID with different bytes → refuses, preserves both packages and existing originals.
4. Quota failure writing recovery backup or journal → no active-key mutation.
5. Failure after each module write, material transaction abort, job write failure and journal progress failure → previous raw values including absence restored; recovery backup remains readable.
6. Kill/reopen after each phase and after write-before-progress → deterministic replay; no mixed editable job/modules.
7. Second window attempts job autosave, source/photo import, architectural commit, material sync, recipe save, sheet rename and price change during restore → blocked or drained before exclusive lease; late async responses cannot write after lease loss.
8. Same-job-ID older snapshot → architecture, materials, pricing, sheet navigation, selections and histories reflect restored state after boot, not cached current state.
9. Different-job restore whose destination modules already exist → destination before-images and previous active job both recoverable; no unrelated projects/global reference rates changed by default.
10. Original PDF/photo byte hashes before/after success and rollback match; no original delete calls are used.
11. v1 legacy package behavior is explicit; v2 null records restore absence; missing module snapshots do not inherit arbitrary current-state data.
12. Inspect desktop/mobile preview, cancel, success, reload and forced-recovery screenshots. Repeat against the actual Dans1 production/native build in isolated profiles; leave the user's normal profile untouched during failure injection.

Suggested implementation order: (a) write gate plus no-regression tests, (b) pure plan and journal adapters with fault injection, (c) startup replay, (d) apply preview/recovery UI, (e) real isolated browser/native proof. Do not expose an enabled Apply button before (a)–(c) pass.
